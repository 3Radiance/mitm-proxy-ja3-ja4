# mitm-proxy-ja3-ja4

[English](README.md) | [Русский](README.ru.md)

HTTP MITM-прокси, написанный на Rust с использованием `tokio` и `btls`.

> **Сейчас проект находится на стадии MVP (Minimum Viable Product).**

Проект был полностью переписан с использованием `btls` (BoringSSL) для реализации расширенных возможностей подмены TLS-фингерпринта. Слой TLS-фингерпринтинга (JA3/JA4) теперь полностью настраиваемый — наборы шифров, кривые, алгоритмы подписи, ALPN, ограничение размера TLS-записи, сжатие сертификатов, GREASE и точный порядок расширений задаются через JSON-профиль. **Encrypted Client Hello (ECH) пока намеренно не реализован** — эта функция находится в планах. HTTP/2-фингерпринтинг (Akamai) уже реализован, следующим уровнем является TCP-фингерпринтинг (L4).

## Возможности (текущая реализация)

* **MITM (Man-in-the-Middle)** — прозрачное перехватывание HTTPS-соединений. Для динамической генерации и подписи сертификатов используется `rcgen`, а созданные сертификаты кэшируются через `dashmap` для повышения производительности.

* **Интеграция с BoringSSL** — используются `btls` и `tokio-btls` для обработки TLS-handshake и MITM-перехвата.

* **Подмена TLS-фингерпринта (JA3/JA4) — полностью реализована, кроме ECH.** Upstream TLS-соединение полностью строится на основе JSON-профиля, переданного через `-c` / `--config <path>` (формат см. в `example.json`):

  * Наборы шифров в строго заданном пользователем порядке.
  * Эллиптические кривые.
  * Алгоритмы подписи.
  * ALPN с учётом протокола, фактически выбранного upstream-сервером.
  * Ограничение размера TLS-записи.
  * Сжатие сертификатов (`brotli`, `zlib`, `zstd`) с полноценной поддержкой распаковки.
  * GREASE.
  * Точный порядок TLS-расширений в ClientHello.

* **Сначала ALPN с upstream-сервером (Upstream-First ALPN Negotiation)** — прокси сначала устанавливает TLS-соединение с upstream-сервером и договаривается с ним о протоколе, ещё до завершения TLS-handshake со стороны браузера. После этого выбранный upstream-сервером ALPN используется для настройки клиентского TLS acceptor. Благодаря этому браузер не сможет выбрать протокол, который upstream-соединение не поддерживает.

* **Подмена HTTP/2-фингерпринта (Akamai)** — HTTP/2-фингерпринт полностью настраивается через JSON-профиль:

  * Значения HTTP/2 SETTINGS и их точный порядок.
  * Обновление окна flow control на уровне соединения.
  * Настраиваемый начальный ID потока с автоматическим вычислением при наличии PRIORITY-фреймов.
  * HTTP/2 PRIORITY-фреймы и приоритет request HEADERS.
  * Настраиваемое расположение `END_STREAM` для пустых запросов.
  * Порядок pseudo-заголовков.
  * Порядок HTTP-заголовков.
  * Замена, добавление и удаление HTTP-заголовков.
  * Потоковая передача request/response body без полного буферизования тела.
  * Поддержка HTTP/2 trailers.

* **Поддержка upstream HTTP-прокси** — возможность проксировать соединения через внешний HTTP-прокси с использованием метода `CONNECT`.

* **Асинхронность** — проект построен на `tokio` и использует высокопроизводительный неблокирующий асинхронный I/O.

## Roadmap и дальнейшие планы

Текущая архитектура является основой для реализации расширенного фингерпринтинга:

* **Encrypted Client Hello (ECH)**

  Пока не реализован — реализация отложена до завершения остальных компонентов системы фингерпринтинга.

* **L4 TCP Fingerprinting (NFQueue)**

  Реализовать Layer 4-модуль с использованием Linux `nfqueue` (Netfilter Queue) для подмены TCP-фингерпринта, включая TTL, размер TCP-окна, MSS, window scaling и точный порядок TCP-опций.

## Требования

* Rust (edition 2021)
* Linux (для будущей реализации L4-фингерпринтинга через `nfqueue`)
* Firefox с [Multi-Account Containers](https://addons.mozilla.org/firefox/addon/multi-account-containers/) (настоятельно рекомендуется для одновременного использования нескольких фингерпринтов)

## Установка и использование

### 1. Сборка

```bash
git clone https://github.com/3Radiance/mitm-proxy-ja3-ja4.git

cd mitm-proxy-ja3-ja4

cargo build --release
```

### 2. Запуск

Все настройки — порт, upstream-прокси и пути к CA-файлам — находятся в JSON-конфигурации, передаваемой через `-c` / `--config <path>`. Отдельных CLI-флагов `--port` / `--upstream` нет.

```json
{
  "config": {
    "port": 9090,
    "upstream_proxy": "127.0.0.1:10808",
    "cert": "/home/radiance-root/mitm-proxy-ja3-ja4/ca.crt",
    "key": "/home/radiance-root/mitm-proxy-ja3-ja4/ca.key"
  }
}
```

Чтобы работать без upstream-прокси, установите `"upstream_proxy": null`.

```bash
cargo run --release -- --config profile.json

# или

cargo run --release -- -c profile.json
```

При первом запуске, если `cert` / `key` ещё не существуют, прокси автоматически создаст CA-файлы по указанным в конфигурации путям:

* `ca.crt` — корневой сертификат CA. Его необходимо импортировать в Firefox/браузер и добавить в доверенные сертификаты, чтобы браузер мог устанавливать HTTPS-соединения через прокси.
* `ca.key` — приватный ключ CA.

## Основные компоненты архитектуры

* `src/main.rs`: CLI-точка входа, использующая `clap` для обработки `-c` / `--config <path>`. JSON-конфигурация содержит порт прокси, upstream-прокси, пути к CA, TLS-фингерпринт-профили и HTTP/2-фингерпринт-профили.

### Конфигурация

* `src/config.rs`: модели JSON-конфигурации и парсеры для всех уровней фингерпринтинга. Здесь обрабатываются TLS-настройки, HTTP/2 SETTINGS, приоритеты потоков, порядок заголовков, переопределение HTTP-заголовков, порядок pseudo-заголовков и другие параметры профиля.

### Proxy Layer

* `src/proxy/tcp.rs`: обработка TCP-соединений, первичный разбор HTTP `CONNECT`, установка TCP-соединения с upstream, извлечение SNI, TLS-handshake с upstream и последующая передача получившегося TLS-соединения клиенту.

* `src/proxy/http.rs`: минимальный парсинг HTTP/1.x запросов/ответов с использованием `httparse`, включая проверку метода `CONNECT` и извлечение целевого `host:port`.

### TLS Fingerprinting

* `src/tls_fingerprint/cert.rs`: динамическая генерация сертификатов с использованием `rcgen` и `btls::x509`. Сертификаты подписываются локальным CA и кэшируются в `DashMap`.

* `src/tls_fingerprint/tls.rs`: настройка TLS acceptor и connector через `btls` / `tokio-btls`, TLS-handshake с upstream, обработка клиентского TLS-handshake и согласование ALPN.

* `src/tls_fingerprint/helpers.rs`: вспомогательные функции для настройки отдельных компонентов TLS-фингерпринта — наборов шифров, кривых, алгоритмов подписи, ALPN, порядка расширений, ограничения размера записи, сжатия сертификатов и GREASE.

* `src/tls_fingerprint/compression.rs`: реализация сжатия сертификатов с использованием Brotli, zlib и zstd.

### HTTP/2 Fingerprinting

* `src/h2_fingerprint/h2.rs`: точка входа HTTP/2-соединения и обработка соединения на уровне HTTP/2. Координирует клиентское HTTP/2-соединение с настроенным upstream HTTP/2-соединением.

* `src/h2_fingerprint/request.rs`: обработка входящих HTTP/2-запросов, построение upstream-запросов, порядок pseudo-заголовков, манипуляции HTTP-заголовками, создание upstream-потоков и координация передачи request/response.

* `src/h2_fingerprint/request_body.rs`: потоковая передача тела HTTP/2-запроса, обработка flow control, управление `END_STREAM` и request trailers.

* `src/h2_fingerprint/response.rs`: передача HTTP/2-ответов, потоковая передача response body, обработка flow control, `END_STREAM` и response trailers.

* `src/h2_fingerprint/upstream.rs`: создание и настройка upstream HTTP/2 client connection в соответствии с активным fingerprint-профилем.

### Структура модулей

Проект разделён на независимые уровни:

```text
src/
├── config.rs
├── main.rs
│
├── proxy/
│   ├── mod.rs
│   ├── tcp.rs
│   └── http.rs
│
├── tls_fingerprint/
│   ├── mod.rs
│   ├── cert.rs
│   ├── compression.rs
│   ├── helpers.rs
│   └── tls.rs
│
└── h2_fingerprint/
    ├── mod.rs
    ├── h2.rs
    ├── connection.rs
    ├── request.rs
    ├── request_body.rs
    ├── response.rs
    └── upstream.rs
```

Слой `proxy` отвечает за работу с низкоуровневым TCP и HTTP `CONNECT`, слой `tls_fingerprint` — за TLS-перехват и TLS-фингерпринтинг, а слой `h2_fingerprint` — за HTTP/2-фингерпринтинг и работу с потоками.

Такое разделение позволяет независимо реализовывать транспортный уровень, TLS и HTTP/2-фингерпринтинг, сохраняя возможность объединять все эти уровни в рамках одного проксируемого соединения.
