# mitm-proxy-ja3-ja4

[English](README.md) | [Русский](README.ru.md)

HTTP MITM-прокси на Rust, `tokio` и `btls`.

> **Сейчас на стадии MVP (Minimum Viable Product).**

Проект полностью переписан на `btls` (BoringSSL) для продвинутого TLS-фингерпринтинга. Слой TLS-отпечатка (JA3/JA4) теперь полностью управляем — наборы шифров, кривые, алгоритмы подписи, ALPN, record size limit, сжатие сертификата, GREASE, порядок/перестановка расширений, OCSP stapling, Certificate Transparency (SCT), session tickets, ALPS и Encrypted Client Hello (ECH, разрешается вживую через DoH, с фолбэком на GREASE) задаются через JSON-профиль. HTTP/2-фингерпринтинг (Akamai) и порядок/подмена HTTP/1.1-заголовков тоже полностью настраиваемы. TCP (L4) фингерпринтинг тоже работает: SYN-пакеты апстрим-соединений переписываются в NFQUEUE (TTL, размер окна, MSS, window scale, флаг DF, таймстампы, точный порядок TCP-опций, марки по доменам) с автоматическим управлением iptables.

## Возможности (текущая реализация)

* **MITM (Man-in-the-Middle)** — прозрачный перехват HTTPS. Сертификаты выпускаются и подписываются на лету через `rcgen`, кэшируются в `moka` для производительности.

* **Интеграция BoringSSL** — TLS-хендшейк и MITM-перехват реализованы через `btls` и `tokio-btls`.

* **Подмена TLS-отпечатка (JA3/JA4) — готово полностью.** Апстрим-соединение целиком собирается из JSON-профиля, который передаётся через `-c` / `--config <путь>` (формат см. в `example.json`):

  * Наборы шифров, в строгом порядке, заданном пользователем.
  * Эллиптические кривые.
  * Алгоритмы подписи.
  * Согласование ALPN на основе протокола, реально выбранного апстрим-сервером.
  * Record size limit.
  * Сжатие сертификата (`brotli`, `zlib`, `zstd`) с реальной поддержкой распаковки.
  * GREASE.
  * Точный порядок TLS-расширений в ClientHello либо случайная перестановка в стиле Chrome.
  * Переключатели OCSP stapling, Certificate Transparency (SCT), session ticket и ALPS (Application-Layer Protocol Settings).
  * Encrypted Client Hello (ECH) — реальный ECH-конфиг разрешается вживую через DoH (запрос HTTPS/SVCB-записи) для каждого апстрим-хоста, причём сам DoH-запрос идёт с тем же TLS/HTTP2-профилем; при отсутствии конфига — фолбэк на ECH GREASE (или ничего), настраивается независимо — подробности в `TLS.ru.md`.

* **Согласование ALPN сначала с апстримом** — прокси устанавливает и согласует TLS с апстрим-сервером до завершения TLS-хендшейка с браузером. Протокол, выбранный апстрим-сервером через ALPN, затем используется для настройки клиентского TLS-акцептора — это не даёт браузеру выбрать протокол, который апстрим-соединение не поддерживает.

* **Подмена HTTP/2-отпечатка (Akamai)** — полностью настраиваемый HTTP/2-фингерпринтинг через JSON-профиль:

  * Значения HTTP/2 SETTINGS и точный порядок SETTINGS.
  * Обновления окна flow-control на уровне соединения.
  * Настраиваемый начальный stream ID с автоматическим вычислением, если заданы приоритетные фреймы.
  * HTTP/2 priority-фреймы и приоритет прямо в заголовке запроса.
  * Настраиваемое размещение `END_STREAM` для пустых запросов.
  * Порядок псевдозаголовков.
  * Порядок HTTP-заголовков.
  * Замена, добавление и удаление HTTP-заголовков.
  * Потоковая пересылка тела запроса и ответа без буферизации целиком.
  * Поддержка HTTP/2-трейлеров.

* **Подмена HTTP/1.1-заголовков** — настраиваемый порядок и содержимое заголовков для апстрим-соединений на голом HTTP/1.1 (когда ALPN не согласует `h2`), по той же семантике замены/удаления, что и в HTTP/2.

* **Подмена TCP-отпечатка (L4) — готово полностью.** Исходящие апстрим-соединения фингерпринтятся на уровне пакетов через Linux NFQUEUE (`src/tcp_fingerprint/`):

  * Переписывание SYN: TTL, размер окна, флаг DF, значения MSS / window scale, тоггл таймстампов, точный порядок TCP-опций (или патч значений на месте, если порядок не задан), с пересчётом чексумм.
  * Очередь установленного соединения правит только TTL/DF (поддержан hop limit IPv6); каждый пакет по умолчанию получает вердикт `Accept`, чтобы очереди никогда не вставали.
  * Маршрутизация по `SO_MARK` на TCP-профили по доменам, автоматическое управление iptables (вставка наверх, выше инструментов вроде zapret/nfqws, дедупликация, удаление при выключении по Ctrl+C) с безопасным `--queue-bypass`.
  * См. `TCP.ru.md` и блок `tcp` в `example.json`.

* **Поддержка апстрим HTTP-прокси** — соединения можно проксировать через апстрим HTTP-прокси методом `CONNECT`.

* **Маршрутизация профилей по доменам** — передай `-d` / `--domain <путь>` с картой доменных паттернов в частичные оверлеи профиля (см. `domain.json`). Каждое соединение сопоставляется по SNI (точное → `*.root` → `*.label.*` → `label.*` → базовый профиль) и обслуживается со своими настройками TCP/TLS/HTTP2/HTTP1/апстрима, предсобранными один раз на старте. Указывать нужно только поля, отличающиеся от базового профиля; остальное наследуется.

* **Асинхронность** — построено на `tokio` для высокопроизводительного неблокирующего ввода-вывода.

## Требования

- Rust (edition 2021)
- Linux (обязателен для L4-функций на NFQUEUE)
- Root или `CAP_NET_ADMIN` (для `SO_MARK`, бинда NFQUEUE и автоматических iptables; без этого ставь `"auto_iptables": false` в блоке `tcp` и применяй mangle-правила руками — см. `TCP.ru.md`)
- Firefox с расширением [Multi-Account Containers](https://addons.mozilla.org/firefox/addon/multi-account-containers/) (настоятельно рекомендуется для одновременного использования нескольких отпечатков)

## Логирование

Прокси использует `tracing` с фильтрацией по модулям через `RUST_LOG`.

Примеры:

```bash
RUST_LOG='H2=error' cargo run --release -- -c profile.json
RUST_LOG='TCP=debug,H2=error,TLS=warn' cargo run --release -- -c profile.json
RUST_LOG='CA=info,TLS=warn,H2=error' cargo run --release -- -c profile.json
```

Поддерживаемые теги совпадают с именами модулей в коде: `TCP`, `HTTP`, `H1`, `H2`, `TLS`, `CA`, `ECH`, `CFG`, `IPT`, `NFQUEUE`, `Runtime`.

Логи по умолчанию содержат таймстамп, чтобы проще было сопоставлять события между собой.

## Установка и запуск

### 1. Сборка
```bash
git clone https://github.com/3Radiance/mitm-proxy-ja3-ja4.git
cd mitm-proxy-ja3-ja4
cargo build --release
```

### 2. Запуск

Все настройки — порт, апстрим-прокси и пути к файлам CA — задаются в JSON-конфиге, который передаётся через `-c` / `--config <путь>`. Флагов `--port` / `--upstream` больше нет.

```json
{
  "config": {
    "port": 9090,
    "upstream_proxy": "127.0.0.1:10808",
    "cert": "/home/radiance-root/mitm-proxy-ja3-ja4/ca.crt",
    "key": "/home/radiance-root/mitm-proxy-ja3-ja4/ca.key"
  }
}
```

Чтобы запустить без апстрим-прокси, укажи `"upstream_proxy": null`.

```bash
cargo run --release -- --config profile.json
# или
cargo run --release -- -c profile.json
```

При первом запуске, если файлы `cert`/`key` ещё не существуют, прокси сгенерирует CA по указанным путям:
- `ca.crt` — корневой сертификат CA. Его нужно импортировать в Firefox/браузер и добавить в доверенные, чтобы сайты определялись корректно.
- `ca.key` — приватный ключ CA.

### 3. Доменные переопределения (опционально)

```bash
cargo run --release -- -c profile.json -d domain.json
```

`domain.json` — карта доменных паттернов в частичные оверлеи, указывать нужно только поля, отличающиеся от базового профиля:

```json
{
  "browserleaks.com": {
    "config": { "upstream_proxy": null },
    "tls": { "enable_ech": false }
  },
  "*.google.com": {
    "tls": { "enable_ech": true }
  },
  "tls.peet.ws": {
    "tcp": {
      "mark": "0x11",
      "ttl": 100,
      "window_size": 64130,
      "mss": 1400,
      "window_scale": 7,
      "dont_fragment": true,
      "timestamp": false,
      "tcp_options_order": ["mss", "sack_perm", "wscale", "nop"]
    }
  },
  "mail.google.*": {
    "tls": {
      "curves": ["X25519", "P-256"]
    }
  }
}
```

Порядок сопоставления для каждого соединения (по SNI, без учёта регистра): точное → `*.root` → `*.label.*` → `label.*` → базовый профиль. Отсутствующий ключ (или `null` везде, кроме `upstream_proxy`) означает «наследовать из базы», а `"upstream_proxy": null` явно форсит прямое соединение для этого домена. TCP-поля (включая `mark`) наследуют базовый профиль так же — `"mark": null` снимает марку для этого домена. Учти: если базовый профиль задаёт `upstream_proxy`, `SO_MARK` не ставится вообще и TCP-слой обходится (см. `TCP.ru.md`).

## Архитектура

* `src/main.rs`: точка входа CLI, разбор `-c` / `--config <путь>` через `clap`. JSON-конфигурация содержит порт прокси, апстрим-прокси, пути к CA, профили TLS-отпечатка и профили HTTP/2-отпечатка.

### Конфигурация

* `src/config.rs`: модель JSON-конфигурации и парсеры для всех уровней фингерпринтинга. Обрабатывает настройки TLS, опции ECH/DoH, HTTP/2 SETTINGS, приоритеты потоков, порядок заголовков, переопределения HTTP-заголовков, порядок псевдозаголовков и другие специфичные для профиля опции.

* `src/domain.rs`: доменные оверлеи профилей (`-d` / `--domain`). Частичные переопределения глубоко мержатся поверх базового профиля один раз на старте; поиск на соединение — дешёвый клон `Arc` без реаллокаций.

### Слой прокси

* `src/proxy/tcp.rs`: обработка TCP-соединений, разбор начального HTTP `CONNECT`, установка апстрим TCP-соединения (маркированные сокеты через `SO_MARK`, если профиль задаёт `mark`), извлечение SNI, маршрутизация на доменный профиль (совпадение по SNI с фолбэком на базовый профиль), согласование TLS с апстримом и связывание полученного TLS-соединения с клиентом.

* `src/proxy/http.rs`: минимальный разбор HTTP/1.x запросов/ответов через `httparse`, включая проверку метода `CONNECT` и извлечение целевого `host:port`.

### TLS-фингерпринтинг

* `src/tls_fingerprint/cert.rs`: генерация сертификатов на лету через `rcgen` и `btls::x509`, подпись локальным CA, кэширование в `moka`.

* `src/tls_fingerprint/tls.rs`: настройка TLS-акцептора и коннектора `btls` / `tokio-btls`, согласование TLS с апстримом, обработка клиентского TLS-хендшейка и согласование ALPN.

* `src/tls_fingerprint/helpers.rs`: отдельные хелперы настройки TLS-отпечатка для наборов шифров, кривых, алгоритмов подписи, ALPN, порядка/перестановки расширений, record size limit, сжатия сертификата, GREASE, OCSP stapling, SCT, session tickets и ALPS.

* `src/tls_fingerprint/compression.rs`: реализации сжатия сертификата для Brotli, zlib и zstd.

* `src/tls_fingerprint/ech.rs`: разрешение реального ECH-конфига вживую через DoH (запрос HTTPS/SVCB-записи, с переиспользованием настроенного TLS/HTTP2-профиля для самого DoH-запроса), с фолбэком на GREASE, если для хоста конфиг не опубликован.

### HTTP/2-фингерпринтинг

* `src/h2_fingerprint/h2.rs`: точка входа HTTP/2-соединения и обработка запросов на уровне соединения. Координирует клиентское HTTP/2-соединение с настроенным апстрим HTTP/2-соединением.

* `src/h2_fingerprint/request.rs`: обработка входящих HTTP/2-запросов, построение запроса, порядок псевдозаголовков, манипуляция HTTP-заголовками, создание апстрим-потока и координация пересылки запроса/ответа.

* `src/h2_fingerprint/request_body.rs`: потоковая пересылка тела HTTP/2-запроса, обработка flow-control, размещение `END_STREAM` и трейлеры запроса.

* `src/h2_fingerprint/response.rs`: пересылка HTTP/2-ответа, потоковая передача тела ответа, обработка flow-control, обработка `END_STREAM` и трейлеры ответа.

* `src/h2_fingerprint/upstream.rs`: создание и настройка апстрим HTTP/2-клиентского соединения согласно активному профилю отпечатка.

### HTTP/1.1-фингерпринтинг

* `src/h1_fingerprint/h1.rs`: обработка апстрим-запросов по HTTP/1.1 (используется, когда ALPN не согласует `h2`), включая настраиваемый порядок и содержимое заголовков, построено на `hyper`.

### TCP-фингерпринтинг

* `src/tcp_fingerprint/syn.rs`: NFQUEUE-консьюмер SYN-пакетов — переписывание window/TTL/DF, пересборка TCP-опций из `tcp_options_order`, пересчёт чексумм, стирание fwmark на вердикте.
* `src/tcp_fingerprint/tcp.rs`: NFQUEUE-консьюмер установленного соединения — только TTL/DF (hop limit для IPv6), всё по умолчанию принимается.
* `src/tcp_fingerprint/iptables.rs`: автоматическое управление mangle-правилами — вставка наверх, дедупликация, чистка при выключении.

### Структура модулей

Проект разделён на независимые слои:

```text
src/
├── config.rs
├── domain.rs
├── main.rs
├── logging.rs
│
├── proxy/
│   ├── mod.rs
│   ├── tcp.rs
│   └── http.rs
│
├── tcp_fingerprint/
│   ├── mod.rs
│   ├── syn.rs
│   ├── tcp.rs
│   └── iptables.rs
│
├── tls_fingerprint/
│   ├── mod.rs
│   ├── cert.rs
│   ├── compression.rs
│   ├── ech.rs
│   ├── helpers.rs
│   └── tls.rs
│
├── h2_fingerprint/
│   ├── mod.rs
│   ├── h2.rs
│   ├── request.rs
│   ├── request_body.rs
│   ├── response.rs
│   └── upstream.rs
│
└── h1_fingerprint/
    ├── mod.rs
    └── h1.rs
```

Слой `proxy` обрабатывает сырой TCP и HTTP `CONNECT`-трафик, слой `tcp_fingerprint` переписывает исходящие пакеты в NFQUEUE до выхода на провод, слой `tls_fingerprint` отвечает за перехват TLS, подмену TLS-отпечатка и разрешение ECH, слой `h2_fingerprint` — за подмену HTTP/2-отпечатка и трафик на уровне потоков, а слой `h1_fingerprint` — за подмену HTTP/1.1-заголовков для апстрим-соединений, не согласовавших `h2`. Такое разделение держит логику транспорта, L4, TLS и фингерпринтинга каждого протокола независимой друг от друга, при этом позволяя слоям работать вместе в рамках одного проксируемого соединения.
